Requested by Josh: the playbook was rewritten Aug 21–26 (pods A/B, Slack only
for domain-retire/backfill/word/EOD, the canary fleet, placement tests) and
the repo underneath it still carries the old world. This audit flags
(1) everything that **contradicts** the new canon, (2) everything **beyond its
scope**, and (3) a phased teardown/rewrite I can execute without breaking
production.

Baseline: `main` @ `b5c60a0`, deployed to Railway 2026-08-26 09:13Z
(service `deliverabilitywizard`, env `production`). Typecheck clean,
**689/689 tests green**, 107 guards green. Source: 141 files / ~35.8k lines
(+123 test files / ~20k lines). Ledger: `DECISIONS.md` D1–D123, 2,779 lines.

The live canon itself is restated in **`CANON.md`** (new, in this branch) —
one page, every rule citing its decision. Roughly **60% of the ledger text
describes superseded behaviour**, which is the core of the "losing the plot"
problem: the dead rules outweigh the live ones in everything an agent reads.

## 10. The teardown/rewrite plan

**Philosophy** (this is the answer to "an extensive rewrite will break the
whole thing"): no big-bang rewrite, because none is needed — the canon
services already exist and run. This is a **strangler teardown**: six phases,
each an independently deployable, independently revertible PR that leaves the
suite green and the board provably no worse. The rewrite happens by
subtraction, and by giving every finding an owner. Grok is right that a
rewrite-in-place of the live loops would break production; that is not what
this is.

**Standing rules for every phase**
- One phase = one PR = one merge = one deploy. No stacking. Merge in a quiet
  window, then watch **one full health pass + one hourly check + one bounce
  pass** (≈65 min) before calling it good.
- Gate: `npm run typecheck && npm test` + guards green locally; after deploy,
  `[canon] open findings` present, `health-pass` recorded OK, no new
  `[watchdog] … FAILED`, finding counts ≤ baseline ±noise, `[slack-quiet]`
  only where expected.
- Kill criteria: any stage FAILED twice consecutively, findings >2× baseline,
  or any unexpected Slack → `git revert` the merge (every phase is
  revert-clean by construction), redeploy, write the failure into this doc.
- Before Phases 3–4: capture `/status` (RUN_TOKEN) as a state-file snapshot.
- Each behaviour-changing phase lands with its own `DECISIONS.md` entry (the
  cleanup itself becomes D-numbered canon, superseding by name) and updates
  `CANON.md` in the same PR.
- The bug remediator's auto-merge is off for the duration (G6).
